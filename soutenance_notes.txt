3. NOTIONS A SAVOIR EXPLIQUER SIMPLEMENT (questions orales attendues)
-------------------------------------------------------------------------------

Q: Comment fonctionnent Docker et docker compose ?
A: Docker construit une image (systeme de fichiers + config) a partir d'un
   Dockerfile, puis lance cette image comme conteneur : un processus isole
   (namespaces + cgroups) qui partage le noyau de la machine hote, contrairement
   a une VM. docker compose lit un fichier YAML (docker-compose.yml) qui decrit
   plusieurs services/conteneurs, leurs volumes et leur reseau, et les
   orchestre en une seule commande (build, creation du reseau, des volumes,
   demarrage dans le bon ordre via depends_on).

Q: Difference entre une image Docker utilisee avec ou sans docker compose ?
A: L'image elle-meme est identique (construite par le meme Dockerfile). Sans
   compose, il faut lancer "docker build" et "docker run" a la main pour
   chaque conteneur, creer le reseau et les volumes soi-meme, et gerer les
   dependances entre conteneurs manuellement. Avec compose, tout est declare
   dans un seul fichier et gere par un seul outil (build, network, volumes,
   ordre de demarrage, restart policy) : plus simple, reproductible, versionne.

Q: Quel est l'interet de Docker par rapport a une VM ?
A: Une VM virtualise un materiel complet + un OS invite via un hyperviseur :
   lourd, lent a demarrer, gourmand en RAM/disque. Un conteneur Docker partage
   le noyau de l'hote et n'isole que le processus/le systeme de fichiers/le
   reseau : demarrage quasi instantane, tres leger, on peut faire tourner
   beaucoup plus de conteneurs que de VMs sur la meme machine. Ici, la VM sert
   uniquement d'hote pour Docker ; chaque service (nginx, wordpress, mariadb)
   est un conteneur, pas une VM a part entiere.

Q: Pertinence de l'arborescence imposee par le sujet ?
A: srcs/ regroupe tout ce qui configure l'appli (compose + .env + un dossier
   par service sous requirements/), separe du Makefile a la racine qui pilote
   tout. Chaque service a son propre Dockerfile + conf/ + tools/ : ca isole
   clairement la responsabilite de chaque conteneur (1 Dockerfile = 1 service
   = 1 image = 1 conteneur), facilite la maintenance et empeche de melanger
   les responsabilites (ex: pas de nginx dans le Dockerfile wordpress).

Q: Explique le docker-network utilise.
A: Un reseau bridge dedie ("inception") declare dans docker-compose.yml. Les
   3 conteneurs y sont rattaches et peuvent se joindre par leur nom de service
   (DNS interne de Docker) : wordpress parle a "mariadb:3306", nginx parle a
   "wordpress:9000". Le reseau isole ces echanges du reseau de l'hote ; seul
   nginx publie un port vers l'hote (443). "network: host" ou "--link" sont
   interdits car ils cassent cette isolation / sont obsoletes.

Q: Secrets vs variables d'environnement ?
A: Les variables d'env (.env, env_file) sont simples mais visibles via
   "docker inspect" ou dans l'environnement du process. Les secrets Docker
   sont montes comme fichiers dans /run/secrets/, pas exposes par
   "docker inspect". Le sujet accepte les deux (le .env est autorise par la
   grille d'evaluation), les secrets sont "fortement recommandes" pour les
   vraies infos sensibles.

Q: Volumes Docker vs bind mounts ?
A: Un bind mount pointe directement vers un chemin arbitraire de l'hote, gere
   en dehors de Docker. Un volume nomme est cree et gere par Docker
   ("docker volume ls/inspect"), reference par son nom dans le compose. Le
   sujet impose des volumes nommes (pas de bind mount direct) mais impose
   aussi que la donnee soit physiquement dans /home/rcompain/data : on
   concilie les deux avec "driver_opts" (type: none, o: bind, device: ...)
   sur un volume nomme "local" -> Docker le traite comme un vrai volume nomme,
   mais les donnees vivent au bon endroit sur l'hote.

Q: Pourquoi mariadbd/php-fpm/nginx sont lances avec "exec" en fin de script ?
A: "exec" remplace le processus shell courant par le processus final au lieu
   de le lancer en sous-processus : le process principal (nginx, mariadbd,
   php-fpm) devient PID 1 dans le conteneur, recoit correctement les signaux
   (SIGTERM de "docker stop"), et le conteneur s'arrete proprement. Sans exec,
   le shell reste PID 1 et le vrai service ne recoit pas les signaux
   correctement -> conteneur qui ne s'arrete pas proprement, ou daemon zombie.

Q: Pourquoi pas de "tail -f" / "sleep infinity" / boucle infinie en entrypoint ?
A: Un conteneur doit rester vivant parce que son processus principal (PID 1)
   est un vrai processus qui tourne en avant-plan (ex: "nginx -g 'daemon
   off;'"), pas parce qu'on triche avec une commande qui ne fait rien. Ces
   patches masquent des daemons qui forkent en arriere-plan (mauvaise
   pratique, le conteneur croit que tout va bien alors que le vrai service a
   pu crasher) et empechent une gestion propre du cycle de vie/signaux.

Q: TLSv1.2/1.3, pourquoi et comment ?
A: nginx.conf force "ssl_protocols TLSv1.2 TLSv1.3;" pour interdire les
   versions plus anciennes et vulnerables (SSLv3, TLSv1.0/1.1). Le certificat
   est auto-signe (genere avec openssl au build de l'image nginx), donc le
   navigateur affiche un avertissement (normal, pas une vraie autorite de
   certification), mais la connexion est bien chiffree en TLS 1.2/1.3.

4. S'ENTRAINER : MODIFICATION DE CONFIGURATION EN DIRECT
-------------------------------------------------------------------------------

L'evaluateur peut demander de changer le port d'un service. Exemple avec nginx
(443 -> 8443) :

  1. srcs/docker-compose.yml : section nginx -> ports:
         - "8443:443"
     (le port interne du conteneur peut rester 443, seul le port hote change ;
     si on demande de changer le port INTERNE, modifier aussi nginx.conf
     "listen" et le Dockerfile "EXPOSE")

  2. Si le port interne change, editer aussi
     srcs/requirements/nginx/conf/nginx.conf : "listen <nouveau_port> ssl;"
     et srcs/requirements/nginx/Dockerfile : "EXPOSE <nouveau_port>"

  3. Rebuild + relance :
         docker compose -f srcs/docker-compose.yml up -d --build nginx
     ou plus simplement :
         make re

  4. Verifier :
         docker compose -f srcs/docker-compose.yml ps
         curl -vk https://rcompain.42.fr:8443/

S'entrainer aussi sur wordpress (port php-fpm 9000) et mariadb (port 3306) au
cas ou l'evaluateur choisisse un autre service : il faut changer le port dans
le Dockerfile/conf concerne(e), ET dans le fichier qui s'y connecte (ex:
fastcgi_pass dans nginx.conf si on change le port de wordpress).
